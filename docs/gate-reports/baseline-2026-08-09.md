## 2. Gate 0 — the break-even inequality, evaluated

A-02's inequality is **S > 11.5 · c · C** (S = tool tokens saved, c = fraction of turns that change
the active set, C = per-request context). With C = 49,964 (p50 measured) and a realistic mounted floor
of five tools (the four workhorses plus a loader), bracketing per-tool definition cost:

| Per-tool tokens | Catalog S | Savable | % of p50 context | c=0.05 | c=0.15 | c=0.40 |
| ---: | ---: | ---: | ---: | :--- | :--- | :--- |
| 150 | 3,000 | 2,250 | 4.5% | loses **13×** | loses **38×** | loses **102×** |
| 250 | 5,000 | 3,750 | 7.5% | loses **8×** | loses **23×** | loses **61×** |
| 400 | 8,000 | 6,000 | 12.0% | loses **5×** | loses **14×** | loses **38×** |

**There is no cell in which mounting pays.** Required savings at the most generous churn rate
(c = 0.05, one mount event per twenty turns) is ~28,700 tokens; the entire catalog is 3,000–8,000
tokens. The intervention is not marginally negative — it is off by an order of magnitude.

**The same result in dollars, which is more visceral:** one mount event costs a full-context cache
write at $3.75/MTok.

- At p50 context (49,964 tok): **$0.187 per mount event — 4.2× the entire median session's total cost of $0.044.**
- At p90 context (223,217 tok): **$0.837 per mount event — 52% of a p90 session's total cost.**

## 3. Why it fails — and it is not the reason the blueprint assumed

The architecture-critic's F4 predicted exactly this and the data confirms it: **the project was aiming
at the smaller term.** Tool definitions are 4.5–12% of a typical request here. History and file content
are the rest. And the two terms have opposite cache behaviour:

- Tool definitions sit at the **head** of the cacheable prefix, are **cheap to keep** (91.1% of prompt
  tokens are served at cacheRead rates), and are **expensive to change** (any mutation invalidates
  everything downstream).
- History sits at the tail, is **appended**, and is therefore **cheap to attack** — compressing it
  preserves the prefix.

A 114:1 cache read/write ratio means this setup is already close to the best case the "just cache the
full catalog" strategy can achieve. There is nothing for JIT mounting to win.

## 4. The boring alternative already won (A-13)

p90 distinct tools per session is **4**, from a catalog of ~20, and four tools account for 98.1% of all
calls. **pi's default core tool set already is the right static profile for this workload.** No
retrieval layer, no capability index, and no eviction policy could improve on "leave the ~20 tools
mounted and let the cache serve them" — there is no selection problem at this scale, only a selection
*cost*.

## 5. What this does NOT show

1. **One catalog, and it is the author's own** — precisely R-13's overfit warning. It says nothing
   about an OSS pi user's catalog (Q-WHO-1's primary user), and the ~110-package ecosystem means other
   users' catalogs could be far larger.
2. **Nothing about accuracy.** B4 and B7 are uncaptured; A-01 remains UNVALIDATED. The economics kill
   the intervention here *before* accuracy becomes relevant, which is why Gate 0 runs first — but a
   catalog large enough to change the economics would also need the accuracy curve.
3. **Nothing about the many-tool product agent** named in Q-WHY-1 pain #3. If that agent is the real
   target, its planned catalog is the relevant B1 and this report does not speak to it.
4. **Nothing about A-11.** No extension here calls `setActiveTools`, so the absence of
   `active_tools_change` entries is uninformative. Version skew also applies (0.83.0 installed vs
   `main` read for the source evidence).
5. **Native deferred loading is not accounted for.** On Anthropic 4.5+/OpenAI Responses gpt-5.4+/Kimi,
   mounting need not invalidate the prefix, which removes the *cost* side of this finding — but it does
   not create the *savings* side: 3,000–8,000 tokens of definitions in a 50,000-token context is still
   not worth engineering for. The conclusion holds on both paths, for different reasons.

## 6. The decision this forces

Gate 0's result is unambiguous **for this catalog** and says nothing about the others. So the open
question is not technical, it is about target:

- **If the target is this pi setup** → the honest outcome is the **O6 park**, executed on measured
  evidence with re-triggers (catalog crossing ~110 tools; a workload whose per-request context is small
  enough that definitions dominate; pi/pi-ai losing native deferral).
- **If the target is the OSS pi community** (Q-WHO-1's recorded answer) → this report is one data
  point, not the population. The next cheapest step is measuring *other* catalogs, and the honest
  product might be the measurement tool itself rather than the mounting layer.
- **If the target is the many-tool product agent** (Q-WHY-1 pain #3) → re-baseline on *its* planned
  catalog, and note that a catalog would need to exceed ~110 tools *and* run in small-context sessions
  before mounting pays.
